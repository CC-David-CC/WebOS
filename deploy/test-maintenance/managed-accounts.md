# Account Management and the four-hour reset

The registered account's immutable subject owns its retention grant, Files home and mailbox binding. A WebOS username is reusable. The Stalwart mailbox used for a resettable user has an internal name derived from the subject. SMTP rewrites the public address to that internal name when accepting the recipient. A message already accepted for one subject cannot be delivered to a later holder of the same username.

| At reset | Account, Files and mail |
| --- | --- |
| Retained | Keep the same subject, Files home, Stalwart account ID, messages and address. |
| Expiring | Disable sign-in and revoke sessions. Block mailbox authentication and delivery, remove the public route, destroy the bound Stalwart mailbox, reload mail routing, and retire the subject's Files home. Remove the WebOS account and release the ordinary address once both stores acknowledge cleanup. |
| Interrupted cleanup | The original subject stays disabled and owns the name while cleanup retries. A later run resumes by subject and mailbox ID. Other expiring subjects can finish independently. |

There is no cooling-off period or expired-address list. Service names such as `postmaster` and `mail-ops` remain reserved. Stalwart performs physical storage reclamation in background. A newly registered user gets a different mailbox ID and begins with an empty inbox.

## Staging and operator checks

1. Use a disposable issuer or a private restored copy. Resolve the initial administrator, retained users, and WebOS-linked pilot accounts to their existing immutable subjects. Reconcile pilot IDs with the Stalwart directory and the existing private SSO bindings. Keep the service-only operations mailbox separate from WebOS user resets.
2. Run `python -m webos_accounts.management /path/to/identity migrate --owner SUBJECT --retain OTHER_RETAINED_SUBJECT --pilot WEBOS_PILOT_SUBJECT` under the issuer service identity with the candidate's packages. Repeat the options for additional subjects. This bootstraps roles, retention and requested mail settings. The live pilot uses its existing mailbox names and SSO bindings. Import or migrate these safely before enabling the managed reset on a live issuer.
3. Run the backend with `WEBOS_ACCOUNT_MANAGEMENT=1` and the signed-in Desktop with the Account Management component enabled. Use **System Tools → Account Management**. The administrator grants or removes retention with **Keep across resets**. Only an administrator with the relevant permission can issue a one-time reset code or change another user's access. A local operator can assign a role using `python -m webos_accounts.management /path/to/identity role grant SUBJECT moderator`. The same command accepts `revoke` or the `administrator` role. Preserve at least one active, retained administrator.
4. The managed reset needs the matching packaged Accounts and Storage code, its updated reset driver, and Files cleanup enabled. For resettable mailboxes, install the loopback Stalwart operator as systemd credential `mail-lifecycle-operator` on the reset service. Its private JSON contains the SMTP host's **Stalwart registry operator** username and secret. SMTP2GO credentials belong solely to the outbound relay. The operator must read and update account roles and recipient routes, destroy the intended Stalwart user, and reload settings.
5. Run `ksu-test-account-reset.sh preview --cleanup-files` with the test site's installed environment and inspect the retained-account, removal and mailbox counts. The preview makes no changes. On the approved schedule, `reset --cleanup-files` uses that transaction's current retention grants. An unacknowledged store operation keeps the identity in `am_retiring`. Restore the dependency and rerun the normal reset. Never release a username by deleting a pending cleanup row manually.
6. The browser mail switches currently record desired grants. Before broad registration defaults are enabled, connect provisioning and the four independent grants to the online operator, verify actual per-recipient enforcement and SSO, and test compatibility with the three existing mailboxes. A policy request in SQLite alone must never enable external sending or be shown as effective delivery permission.

## Qualification and rollback

The lightweight regression suite is `test_reset_files.py`. Run with the candidate's backend packages on `PYTHONPATH`. The independent Accounts suite is `tests/test_management.py` in the Accounts repository. For the real SMTP and JMAP rehearsal, `deploy/mailcraft/verify_reset_fixture.py` expects an isolated loopback network namespace, a disposable configured Stalwart server on JMAP port 28881 and SMTP port 2025, the pilot denial/receive roles, a private `online-operator.json`, the candidate backend packages, and an unused private working directory. The fixture registers temporary subjects, delivers messages, and destroys only the fixture mailbox selected by the reset. It also finishes a message whose recipient was accepted before reset after the address has been reassigned.

Keep the previous viewer and backend receipts and capture the policy database, Files metadata and mailbox bindings privately before activation. To roll back a staged UI, restore the previous viewer. If the managed account schema has been enabled, pause resets and provisioning before reverting enforcement code. The legacy reset understands two fixed usernames and cannot represent new retention grants. Restore reader-compatible code and rerun preview before resuming. Do not roll back a live mail store or account database over messages or accounts created since deployment.
