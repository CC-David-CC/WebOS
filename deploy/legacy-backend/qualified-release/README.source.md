# Main-only conservative release candidate (research; not activated)

The user requires no games on main and only finished, end-to-end tested features; beta remains the development site. This candidate is a conservative **proposed** core, not proof that every retained feature is fully finished: Files, Text, Terminal, Calculator and Help, with CodeMirror as Text's dependency. `docs/APP_STATUS.md` calls the first four workflows checked and Help's static information checked, but describes real limits; the integrated signed test below is not a comprehensive end-to-end qualification of them on live main. Do not describe all previously present non-game apps as finished. Release needs core workflow checks and independent review; missing apps and their saved files remain on beta/unchanged.

The candidate was built only from the exact public `0965a0cbdd022f588061cdc23e10eb6b18fa5977cc3f6a05569439eaf11d2020` main tree. It excludes 68 of 74 catalog entries, including 28 games and unfinished Microduck, removes the Games menu and seven disabled learning-game labels, uses a five-app central UI admission check for launch/open/layout restore, and leaves saved `.game.json`, `.brf` and other unadmitted-app projects unchanged while directing users to beta. It also hides account-created app launch entries without deleting them. The six catalog entries are `calculator`, `files`, `help`, `terminal`, `text`, `codemirror`. The remaining main asset graph contains no excluded app bundle directories; old names/icons and unsupported helper branches remain in app.js/desktop-apps.js as inert code, and voice/keyboard controls remain in System Tools. `codi-featured-chess.service` and official endpoints were not changed; whether any separate route constitutes a game experience still requires assessment. Microduck is a physics/robotics simulator listed under Games, kept on beta because its workflow remains unfinished, not classified here as inherently a game. Beta's Microduck runner/CSP is a separate unqualified issue.

## Bounded tests

- `signed-fixture.py` wraps the existing disposable signed issuer/gateway fixture, serving an isolated hardlinked candidate copy on the **same filesystem** as `TMPDIR`; it turns off that fixture's OPFS override to resemble main's v1 configuration, but uses c046/44da and a fixture issuer, not the actual main gateway/issuer. Chromium `signed-candidate.test.cjs` registered an account, opened the actual Applications menu, exercised all 68 excluded IDs via both direct `launch` and document `open`, checked game asset 404, filtered catalog, and restored a mixed saved layout with only Text retained. A `.game.json` file was written and synced; opening it and a `.brf` path did not open games, and saved bytes remained. Files and Text mounted. Synthetic layout and direct method calls are not physical touch or a complete real-app walkthrough. The fixture does not use real Linux guest. A first run attempted cross-filesystem hardlinks and correctly failed `EXDEV`; setting a same-filesystem `TMPDIR` fixed the fixture without touching the candidate.
- `cache-transition-fixture.py` and `cache-transition.test.cjs` use real Chromium service workers and a loopback static server; an existing 0965-controlled tab saw the old game catalog while the new worker waited, then after that tab closed a new tab saw no game and its asset returned 404. A synthetic IndexedDB sentinel survived. The first attempt failed because the loopback fixture omitted `Service-Worker-Allowed: /`; adding the same header as managed Caddy fixed the fixture. This is not an actual main account migration test. Existing open or offline-controlled tabs can keep old cached game code until updated/closed; a server release cannot retract already loaded code.

These tests did not qualify the full supported Files/Text/Terminal/Calculator/Help workflows against actual main, other-account denial, mobile, 4K, guest readiness, beta regression, all-site hosting behavior or crash/recovery. Complete those before calling the candidate finished or activating it.
