# Signed Files probe candidate

`ops/beta_signed_probe.py` is an isolated candidate, not installed or bound to the production launcher. Its dedicated account must only be provisioned by an authorized operator under the existing host lock and in an account-independent private 0700 directory, with its 0600 configuration and journal excluded from artifacts and logs. The protected launcher must verify all directory ancestors and pin the policy, code, issuer and gateway before calling it. It must use the actual beta origin and private service ports. Never use a person's account.

`provision_private` journals registration intent before signup and file creation intent before creating a fixed known record; it publishes the private account configuration only after a verified signed read. Interrupted or ambiguous provisioning leaves the journal and requires explicit reconciliation; repeating provisioning is rejected. The journal contains credentials and must remain private. Probe recovery should use `read_known` (no mutation); the explicit acceptance test runs `acceptance` to create/read/delete/check absence of a random record, retaining its private journal on ambiguity. No dispatched mutation is blindly retried. Reconcile a remaining record under the same dedicated account before deleting its journal. This protocol does not promise power-loss behavior beyond the fsync calls or protection from a trusted administrator bypassing the operator.

`tests/beta-signed-native-fixture.py` and `tests/beta-signed-probe-test.py` exercise an isolated local signed account, real pinned 166→853 issuer process replacement and pinned gateway, preserving disposable account state. The test provisions privately, verifies issuer authority/account continuity and a known file, performs signed create/read/delete/absence, injects a lost reply after an actual successful create and checks the retained journal, and rejects wrong data and public credential permissions. This injected lost reply is not a socket-cut test. The fixture verifies complete sealed native/gateway inventories after shutdown. It does not exercise systemd, the assembled floor transaction, actual protected launcher, or live beta.

Before use, implement and review a concrete protected-launcher binding which checks the existing held lock, verifies code, all credential ancestors, policy/issuer/gateway pins and service routes, calls signed read health at the appropriate gate/forward checkpoints, and fails closed on unknown state. Add real-service floor-transaction integration and interrupted-provision/recovery tests. The issuer switch must remain after the durable v2 floor and while the gate stays active. Do not claim deployment readiness or run the candidate on webhost yet.

The opt-in signed variant of `tests/beta-files-assembly-caddy-test.py` now wires `SignedHealth` into the assembled floor transaction: it provisions a disposable account, kills the transaction immediately after the durable floor, recovers under the held fixture flock, switches the real pinned issuer 166→853 while gated, then performs a signed known-file read during forward/final health and signed create/read/delete/absence after recovery. The real gateway and issuer run in separate local processes; the assembly's service-manager actions and custody callback remain simulated, and Caddy uses a synthetic test route. It rejects running signed health outside its lock and a failed custody callback. The original seven-phase simulated-service control still passes. All release inventories passed after fixture shutdown. This establishes the signed-health callback contract, not an installed protected launcher or production systemd proof. A protected launcher must provide real custody and exact artifact checks; a caller-provided check callback alone is not evidence of those checks.

`beta_files_host_health.create` supplies a concrete fixed-origin, fixed-ports v2 health callback: it requires the existing host lock and root; checks protected probe/policy paths, full pinned 853 native and dd8 gateway inventories, the exact derived issuer and original dependent unit bytes and running unit identities, main readiness, pinned policy and v2 issuer/frontend identity, then performs the signed known-file read. The protected launcher must still load this module, the signing modules and JOSE from individually pinned protected code and call the result from the actual Files assembly; this wiring is not yet installed or implemented. The v2 health callback requires all three beta services active, so an intentionally inactive dependent service makes it refuse rather than claim health. The isolated `beta-files-host-health-test.py` uses simulated root, custody and services to verify missing-lock, custody, native/gateway pin, service and identity refusal; it is not a systemd test.

`beta_files_launch.py` is an **unqualified candidate entrypoint**: it embeds pins, checks root/hostname/protected source, loads the reviewed assembly and real host adapters, and binds the signed host health callback for plan/apply/recover. It is not installed or approved for execution against beta. In local negative controls, a root-owned disposable copy refused a world-writable dependency and a changed pinned source before accessing host state. The executable has not yet completed an isolated full protected-host apply/recover test or independent review; the previously passing assembly tests exercise its building blocks, not this exact entrypoint. In particular test exact module loading and snapshots, same-lock identity, real service and timer behavior, failed/low-space forward recovery and interrupted gate/issuer/exposure before considering it for use. No success or automatic gating is claimed for missing, malformed or unavailable prerequisites. The installed old launcher remains unchanged and continues to refuse apply/recover.

`tests/beta-files-launch-refusal-test.py` reproduces the actual executable's two root-owned disposable-bundle refusal controls. Its hostname substitution is confined to a test process; no host configuration is touched. The candidate now checks distinct beta service accounts and beta/main state-directory isolation at each artifact preflight, and checks other-site health when applying routes. Those checks do not replace the outstanding exact-executable recovery test or review.

The entrypoint also requires a signed known-file read under the same dedicated identity against the old issuer before gate/transition; the signed v2 read is still required after the issuer switch. This control is currently source-level only for the exact launcher. Its full transaction and outage recovery remain unqualified.

Ordering correction: `FilesAssembly` now requires an explicit pre-normalization callback under the hosting lock before any source or journal write, and an explicit custody callback before recovery of a pending normalization journal. The candidate entrypoint binds these to pinned artifact/custody checks; the apply path also requires reserve, Caddy and signed baseline readiness. Isolated failure controls verify unchanged routes and retained journal on rejection. This does not resolve the still-open exact-entrypoint apply/recovery qualification.

## Exact launcher namespace experiment

The exact root-protected entrypoint was run under `python -I -B` in a private mount namespace, against a disposable staged public 0965 release, both retained guarded overlays, 3ad candidate, 853 native release and dd8 gateway. Their full pinned inventories were checked by the launcher. Distinct synthetic beta Unix identities and account directories were validated using the actual isolation code; the real hosting flock, generators, inventory checks, journal writers and source transitions executed in fixture directories. `beta-files-launch-ns-setup.py` and `beta-files-launch-ns-bootstrap.py` preserve the fixture setup and external-dependency shims; these scripts are experimental; the runner below now stages the explicitly supplied public inputs and signed-native fixture automatically.

Outcomes: (1) `plan` initially rejected the distinct-UID fixture because the launcher passed the Caddy UID as the owner of generated auxiliary Caddyfiles, whereas actual managed webctl writes root:caddy. The launcher now passes UID 0; `plan` passed with root:caddy fixture files. (2) An initial `apply` reached and durably wrote the floor and gate but failed because the fixture's simulated systemd hook had patched a function rather than its captured default; this was a fixture failure, and the gate and journal remained. After correcting the fixture hook, `recover` was killed with SIGKILL after the 853 unit was written and before the simulated daemon reload; a second recovery returned `v2-verified`, with the 3ad route and 853 unit, durable floor retained and transaction/issuer journals cleared. (3) After resetting only disposable state and provisioning a new disposable signed account, a clean `apply` returned PASS and a further `recover` returned `v2-verified`. Native and gateway source inventories passed again on fixture shutdown.

Scope: the production launcher and its protected source were unmodified by fixture hooks. The shim substitutes **main-site readiness**, beta Caddy validation/reload and route responses, systemd/timer commands, and the production issuer-policy pin/origin with a disposable issuer. The signed issuer and gateway, probe account, hosting flock, filesystem custody checks and file transactions were real within the isolated fixture. The Caddy/route simulation means this is not a qualification of actual production Caddy/systemd behavior. Separate copied-controller real-Caddy tests cover part of that boundary, but no single test currently combines all real production boundaries. No host accounts, production keys or private main configs were copied. The real main managed-config hashes and active services were separately checked read-only on box-webhost and matched their pinned values at the time of the test; this does not prove fixture transaction behavior.


## Reproducing the namespace experiment

From a fresh checkout, run `python3 -B research/beta-isolated-hosting/tests/beta-files-launch-ns-runner.py` with all eight explicit inputs:

```sh
python3 -B research/beta-isolated-hosting/tests/beta-files-launch-ns-runner.py \
  --baseline /path/to/public-0965-release \
  --overlays /path/to/public-beta-overlays \
  --candidate /path/to/public-3ad-candidate \
  --native-old /path/to/sealed-166-native \
  --native-new /path/to/sealed-853-native \
  --gateway /path/to/sealed-dd8-gateway \
  --python /absolute/path/to/fixture-python \
  --caddy /absolute/path/to/caddy
```

The overlays directory must contain both `1d6b8f4e…` and `bc3c7e65…` public subdirectories. The issuer fixture verifies the complete sealed native and gateway inventories before and after execution; the launcher verifies the public baseline, overlays and candidate and the staged native/gateway again. Inputs are public artifacts only: **do not supply production credentials, account directories, keys or private configurations**. Python needs `aiohttp` and `cryptography`; Caddy must run locally. The runner requires Linux mount namespaces, `mount`, `sudo -n` root, and unused loopback ports 19771–19775. It creates its own root-owned bundle and throwaway filesystem; it kills the test launcher at the issuer-unit change, checks forward recovery, resets the fixture and verifies a clean apply plus idempotent recover. It terminates its issuer fixture and deletes only the two directories it created. Cleanup failures are errors.

The runner deliberately substitutes main readiness, simulated beta service-manager/timer actions and Caddy validation/reload and HTTP route responses. It maps the beta issuer-policy origin/key to a newly created disposable signed issuer in the test process. The source and protected entrypoint are unchanged, and the actual artifact, account-directory and lock checks run, but these substitutions limit the result: it is **not** a real-systemd or real-Caddy production qualification. A first automated-run attempt failed when the unprivileged driver tried to inspect a root-private journal; it was corrected to perform the check through sudo, and the rerun passed. No real site state was touched.

## Combined disposable Caddy and systemd controls

Add `--real-caddy --real-systemd` to the runner command above to run the extended fixture. On 2026-11-04 it passed clean apply, SIGKILL immediately after the 853 issuer-unit write, forward recovery, and a second idempotent recovery. The runner additionally verifies that all three temporary units are active afterward and that the fixture issuer process was actually restarted; temporary units and loopback listeners were gone after cleanup. An initial attempt exposed a fixture variable-name collision, fixed before the passing run. A later run completed the transaction but reported a cleanup failure because `systemctl reset-failed` returned nonzero for unloaded units; cleanup had in fact removed them, and the runner was corrected to stop/remove/reload and to report PASS only after successful cleanup. The final rerun passed.

The extended fixture runs a real, short-lived loopback Caddy per launcher invocation. It validates and reloads a **test-translated** copy of each generated configuration, redirecting domains/ports and replacing the unrelated private hardware-user import. Gate and candidate HTTP checks reach that Caddy and the exact staged 3ad bytes. The launcher's own managed source, generated outputs and inventory checks still use the unmodified pinned production snapshots. This is not a production TLS/ingress test and does not prove the unmodified Caddyfile runs on webhost.

The runner also installs three randomly named, temporary `/run/systemd/system/codi-files-test-*` sleep services with real `Requires`/`After` relationships. The launcher's systemctl operations are mapped to those real units; the fixture translates their `FragmentPath` back to its isolated beta unit path. It independently runs the signed disposable issuer and gateway, which are **not** themselves the systemd services. The production timer remains simulated. Main-site readiness, beta policy/origin, public-site checks and the systemd unit-name/path mapping remain explicit test substitutions. This is stronger than the earlier simulated-service fixture but is not a test of actual beta systemd units or all production dependencies in one transaction. No live site or production account/key data was changed.

## Post-floor missing-artifact gate candidate

The operator bundle now includes `ops/beta_files_candidate.json`, the exact public 3ad manifest (SHA-256 `3ad04c48e60caa559e7b4c56ff624b50a23c093f0dacbc339ca8df147fd009bc`), so the reviewed route snapshots can be reconstructed if the deployed asset tree is unavailable. It is required protected bundle source, not user data. Its hash is checked by `beta_files_snapshots.build`; the candidate asset tree and new native inventory must still be present and verified before any forward exposure.

The managed router has a distinct gate-readiness check: it requires the held hosting lock, protected journal/controller ancestry, the exact installed guarded-controller pin and active Caddy, but not the forward issuer or candidate. Real route inventory, timer, exact-snapshot and post-reload gate-health checks still apply. With a valid committed floor and no pending transition journal, a failed v2 health check attempts the same managed gate. It reports a **verified** gate only after that gate's health check; a failed or unknown gate reports closure unverified. Once the gate is verified, recovery creates a durable forward journal from the validated floor before attempting activation. If the 853 issuer is already finalized, the forward path re-verifies its exact unit/dependent pins and active signed health instead of trying to reinstall an old issuer. Unknown state and corrupt/mismatched floors still refuse; the source does not claim a gate exists after refusal.

Add `--gate-faults --real-caddy --real-systemd` to the namespace runner command above. Its exact-launcher fault cases pass for (1) missing 3ad or 853 before the floor: apply refuses without exposing v2; (2) missing 3ad after committed v2: gate is reached and independently checked by loopback Caddy, then restored assets permit verified forward reopening; and (3) missing 853 after committed v2, with SIGKILL during the gate Caddy reload: recovery completes the gate-only journal, refuses forward activation while 853 is absent, and reopens only after restoration and full forward/signed checks. The 3ad asset tree and 853 native tree are moved only within the runner's disposable public-artifact copy and always restored in cleanup. A separate assembly control rejects malformed floors and distinguishes unverified closure from verified maintenance. The fixture retains the documented test-policy mapping, systemd unit-name/path mapping, main readiness and timer substitutions; it does not activate beta or qualify actual production ingress. This candidate needs independent review before installation.

The `--gate-faults` runner also removes each forward artifact in turn immediately after the durable floor and an interrupted issuer-unit write, before candidate exposure. Each recovery refuses forward activation and retains the maintenance gate; restoring the artifacts permits the signed forward recovery. This extends the before-floor and already-exposed-v2 cases above.

Independent review identified three follow-up issues in the first gate candidate: apply finalization could fail after the outer journal was cleared without attempting a gate; finalized candidate health checked app.js but not the rest of 3ad; and eager dd8/JOSE loading could stop recovery before gating. The follow-up uses the same finalize-or-verified-gate handler in apply and recover, requires complete pinned artifacts in candidate health, and loads JOSE lazily from the verified dd8 bundle under the lock only when signed operations need it. Forward exposure still requires all original artifact and signed checks.

The expanded `--real-caddy --real-systemd --gate-faults` exact-launcher run passed additional controls: an unavailable guarded controller reports gate closure **unverified**; removal of `assets/desktop/apps.json` while app.js remains and removal of the dd8 worker each lead to a verified maintenance gate; and an injected final signed-health failure after the outer journal is cleared during apply also closes the gate while retaining the issuer journal. Restoration and verified forward recovery passed in each case. These results retain the same documented fixture substitutions and do not establish live production behavior. The independent review remains required before installation.

An uncatchable process death cannot itself execute a gate transition. A recovery actor must run; the retained floor and applicable issuer/transition journals support that recovery. These tests do not claim the gate becomes closed instantaneously on SIGKILL.

The extended runner defaults to Caddy ports 19936/19937; pass `--caddy-port` and `--caddy-admin-port` to select other unused loopback ports when needed. Issuer fixture ports remain 19771–19775.

## Sealed processes under disposable systemd units

The runner's `--real-services` option requires `--real-caddy --real-systemd`. It replaces the previous sleep stand-ins with the sealed 166/853 issuer, 166 frontend and dd8 gateway processes under three uniquely named real systemd `DynamicUser` units with distinct UIDs and private runtime directories. A separately named, disabled-but-active real timer is mapped to the launcher's timer operations. Public code/venv inputs are provided to those units through uniquely named read-only bind mounts under `/run`; a separate sparse `size=5200M` tmpfs supplies only tiny disposable test data, so its nominal capacity is not a preallocation and this is not a 128 MiB or RAM-capacity qualification. The actual systemd unit names, paths and timer are fixture-only mappings; main readiness, public production health and the beta issuer policy/origin remain simulated. The native/gateway processes and signed disposable account are real. No production credentials, services, accounts or private configurations are copied.

With the public inputs listed above, use `--real-caddy --real-systemd --real-services --kill-stage STAGE`, where `STAGE` is `unit-write`, `reload`, `restart`, or `timer-stopped`. All four stages passed locally: each completed signed old→new issuer continuity, interrupted recovery, a separate clean apply and idempotent recover. The timer-stopped case checked a pre-floor journal and confirmed the real fixture timer returned to active while remaining disabled. Source code/command-line checks confirmed the expected old and new sealed executables and three distinct non-root DynamicUser UIDs. The runner verifies the complete staged 166/853/dd8 inventories before the real services start. Service outputs are sent to null, so no probe credentials enter systemd logs.

Initial fixture attempts exposed test-setup-only issues: systemd private `/tmp` hid the test code, a preserved DynamicUser runtime path was a symlink rejected by the issuer, and the first gateway test storage was either on the wrong filesystem or below the gateway's unchanged 5 GiB reserve. The fixture now uses read-only `/run` bind mounts, canonical private runtime paths and the sparse throwaway tmpfs. One debug run sent startup diagnostics to the journal only before any account was provisioned; the normal unit configuration sends output to null. One initially failed temporary runtime directory was explicitly removed. The normal runner removes only its uniquely named units, bind mounts, timer, synthetic state and temporary directories; verify cleanup results rather than assuming success. No live beta or main services were changed. This is a more realistic integration fixture, but it is not production beta-unit, production-timer, real public TLS/ingress or 100-user qualification.

The earlier real-service runs used a separate `issuer-next` fixture marker to select the new executable, so they do not by themselves prove the operator-written unit caused the switch. The revised fixture removes that marker. At mapped systemd daemon-reload, `beta-files-launch-systemd-map.py` reads the exact namespace issuer unit produced by the operator, accepts only the pinned old/new unit hashes, checks the issuer ExecStart and OPFS flag, and atomically changes the disposable systemd unit's explicit old/new executable argument accordingly. The fixture trampoline execs the corresponding sealed tree solely from that mapped unit argument. For each run, an old unit must fail the 853 health check; an altered operator unit must be rejected without changing the disposable unit. The mapping is test-only; the production launcher and operator unit bytes are unchanged.
