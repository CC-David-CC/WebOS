# Experimental managed OPFS binding

This branch is based on beta-hosting-isolation `cf04068aa1a428c56237decf114ad89bf34de196`; `opfs_floor.py` copies the journal component from desktop research `3606918ee`. These files are a candidate library only, not a CLI, installed service or authorization to deploy. The installed plan-only launcher is not changed.

`HeldAdapter` calls the existing `beta_transaction.Transaction` using a `ManagedWebctlAdapter` while the caller already holds the existing host lock. It checks that exact lock at entry/exit instead of taking it recursively. `ManagedBinding` uses exact supplied baseline/gate/candidate hosting snapshots. Every normal route transition goes through the existing Transaction and managed adapter. The gate is the old snapshot for the post-floor candidate transition, so an uncommitted nested rollback returns to the gate. Recovery checks for a floor **before** reconciling nested state; a post-floor journal that names the old baseline is rejected. The outer floor remains durable and recovery actors must match its pinned baseline/candidate identifiers. The caller must pin the callbacks, adapter, snapshots and package itself.

`tests/opfs-managed-test.py` uses the actual `ManagedWebctlAdapter` and Transaction against disposable managed files and a real local Caddy process. A test-only controller validates/reloads a generated loopback Caddyfile. It injects a fault into the nested forward transaction, observes managed recovery to the gate then forward to the candidate, and verifies one outer flock per action. It rejects a nested pre-floor rollback after the floor. The pre-existing `tests/maintenance-transaction-test.py` and `tests/generator-test.py` were also run and passed independently; they exercise the existing generated gate and managed transaction tests, not this combined flow. The separate desktop research floor tests exercise subprocess termination, actual journal files, stale actors and rename/fsync faults with a fixture adapter.

**Not production-ready:** a protected launcher must bind actual pinned generator snapshots, managed render-target inventory, Caddy active-state and all-site checks, exact beta issuer service switch and restoration, retained static assets, test account/key custody, source drift, independent service health, timer state and 5-GiB disk reserve. The fixture substitutes a file marker for the issuer and stubs these checks. It does not test actual systemd, live routes, real issuer changes, host power loss or every crash boundary of the two nested journals. A malformed/forbidden pending managed journal is rejected, but this binding cannot guarantee that a separate gate is re-established while the existing controller refuses the malformed journal; the candidate could remain reachable. A reviewed fail-closed recovery mechanism is required before deployment. Paths and callback code must be root protected. Running ordinary hosting recovery after the v2 floor without these checks can re-expose v1 and is unsafe.

Run isolated fixture with `CODI_CADDY=/path/to/caddy python3 -B research/beta-isolated-hosting/tests/opfs-managed-test.py`. It listens only on disposable `127.0.0.1:19988`/`:19989` and does not touch a host Caddyfile or live services.

## Gate-only rescue experiment

The previous test intentionally demonstrated that a malformed or forbidden ordinary inner journal could leave the pinned candidate reachable. `opfs_gate_rescue.py` is a candidate-only gate transition using the same `ManagedWebctlAdapter`, existing `Transaction`, held host lock, and an independently protected emergency journal. After the floor, `ManagedBinding.gate()` invokes that rescue when normal inner-journal preparation rejects. Rescue accepts only exact caller-pinned candidate and gate snapshots; it preserves the original ordinary journal byte-for-byte. A real local Caddy test confirms both malformed and forbidden-v1 ordinary journals leave the exact gate served after the operation, and retrying ordinary recovery does not restore v1. Unknown source bytes, refused custody, or a corrupt emergency journal are not overwritten; the fixture explicitly observes that the candidate may remain reachable in those cases. Timer state is checked in the fixture.

A process-kill test interrupts an actual managed candidate→gate transaction after the Caddy reload. **Negative control:** existing `Transaction.recover()` first restores its prepared transaction's old candidate endpoint, and the test verifies the candidate is actually served before the rescue subsequently transitions back to the gate. Thus this experiment converges to the gate on successful retry; it does **not** prove uninterrupted gating after a crash. If rescue itself cannot run, reports an error, or is interrupted before retry, no successful gated status should be claimed. Journal bytes, source drift and timer errors must remain available for investigation.

This still has no production launcher binding or independent ingress stop. A production mechanism must use root-protected immutable callbacks and snapshot pins, check the real gate and main-site health, preserve timers and account/issuer state, coordinate nested recovery and crash restart, verify actual exact generator/render inventories and capacity, and guarantee the intended access policy during recovery. Actual systemd issuer control and fault behavior are not tested here. A rejected corrupt emergency journal or unknown source can leave the candidate accessible; operator alerting and a separately reviewed way to regain a known safe state are unresolved. Do not run generic ordinary-hosting recovery against the retained forbidden journal after the v2 floor.

The real-Caddy fixture also intentionally bypasses `ManagedBinding` and calls the unchanged generic `Transaction.recover()` directly on the retained forbidden pre-floor journal. **It restores and serves the v1 baseline despite the floor.** The wrapper's refusal is therefore not a global enforcement boundary. Any eventual protected launcher must make every old/unwrapped recovery entry point unable to run after the floor, or use another independently reviewed enforcement mechanism. Until that is implemented and tested, the requirement that ordinary recovery cannot resurrect v1 is not satisfied and activation remains blocked. Unknown custody, unknown timer, corrupt emergency journal and unknown route tests likewise retain evidence and refuse mutation, but intentionally observe that candidate access can remain available.

## Protected recovery entrypoint proposal

`ops/opfs_recovery_entry.py` is a **candidate dispatch helper**, not an installed CLI. It acquires the same existing host lock, checks floor-directory custody, performs `lstat` on the protected floor (including refusing a symlink or malformed-but-present floor), and refuses the legacy recovery path whenever it exists. Only when no floor exists does it verify the exact pinned managed journal under that lock and call the existing Transaction through `HeldAdapter`, without reacquiring the lock. The actual local Caddy/ManagedWebctlAdapter fixture checks that a pinned pre-floor recovery still works and that the same supported dispatch after the floor refuses before touching the journal or routes. The unchanged generic Transaction bypass negative control remains in the test and demonstrates why this wrapper by itself cannot protect the host.

The smallest proposed launcher integration is to pin/import this helper in the root-owned reviewed bundle and replace the launcher's direct `Transaction(adapter,journal).recover()` dispatch with `recover_legacy(...)` using its existing HostLock/check, root-protected 0700 floor parent and exact-journal pin verifier. Keep the currently installed plan-only launcher plan-only until the full new operator has been reviewed. A separate explicit v2 recovery action would enter the gate/floor coordinator and emergency transaction, with approved exact snapshots; it must never route through the old prepared rollback. Installer custody needs root-owned immutable code and manifest/source pins, no-follow path and ownership checks, no writable ancestors, existing systemd unit/config pins, account/key isolation, retained old immutable URLs, exact current live source/render pins, real beta/main health, and reserve plus staged/rollback capacity on the actual filesystem. Fresh free-space and lock/inode checks are required before mutation.

The ordinary `webctl_live.py` also exposes whole-site `activate`, `private`, deployment and other Caddy application operations (and a private-only `caddy-rollback`) outside this helper. The supported operator surface cannot claim global enforcement merely by wrapping `beta_launcher.py`: every authorized controller entry that can change beta's generated routes must either enforce the same floor under the same host lock with pinned beta snapshots, or refuse such changes while the floor exists. Non-beta site operations should remain possible only after verifying their generated beta configuration remains on a pinned v2/gate route; this requires a reviewed generator/render-inventory integration. Deliberately executing unwrapped Python or hand-changing root-managed files as an administrator is outside the protected entrypoint contract, and is not technically prevented by this library.

Forward-only emergency recovery can reuse the existing managed controller and beta-only generated gate without intentionally changing other sites, provided the launcher supplies exact complete generator/manifest/Caddy snapshots and validates every generated auxiliary output plus real main-site health. The current local fixture uses a single synthetic site and does not prove that preservation. Its prepared emergency journal may transiently return to the pinned candidate before gate convergence; unknown/corrupt state can leave it reachable and must be reported as `gated=false`/blocked rather than success. No root installation, launcher modification, or live activation is included in this candidate.

## Versioned gate-only managed journal

The earlier candidate-restoration negative control above is historical for version 1. `beta_transaction.Transaction.apply_gate()` now creates a **version 2, `gate-only`** journal; `recover_gate(expected_candidate, expected_gate)` requires exact pinned endpoints and chooses the gate in both prepared and committed states. The original `recover()` refuses this policy; the actual prior version-1 transaction implementation also refuses it. `GateRescue` uses only these gate-specific methods for its protected emergency journal. Ordinary version-1 transaction behavior is unchanged. Pinned existing launcher manifests must be updated and reviewed before any such code could be installed.

The disposable managed/Caddy test forks and kills actual processes at eight points: journal durable, timer stopped, both source writes, reload intent, reload complete, journal committed, and timer restored. It verifies that old/current ordinary readers and a mismatched endpoint are rejected without mutation, and that gate-only recovery never reloads the candidate. The gate remains the intended recovery target even if the interrupted transaction was only prepared. An interrupted operation may have left the original candidate reachable **until a recovery actually executes**; unknown source/custody, corrupt journals, real service readiness failures or unavailable Caddy can prevent recovery, and refusal is not proof that the site became inaccessible. The test uses a disposable timer adapter and one synthetic site, not real systemd, all-site preservation, automatic crash restart, or power-loss durability.

The separate, pre-existing **version-1** ordinary journal negative control still demonstrates that directly invoking generic recovery can resurrect the v1 baseline despite the OPFS floor. The protected entrypoint and all other host-controller paths must enforce the floor before any live change. This policy is not a production launcher, service installation, or approval to deploy.

## Copied-controller and maintenance inventory fixture

`RenderInventory` now offers an explicit `maintenance_only=True` policy. Both complete manifests must validate, explicitly contain boolean maintenance values, retain the same configured beta release, differ in that boolean, and match in every other top-level field and every site entry. Existing default and `baseline_only` behavior remain unchanged. Tests reject release changes, a site edit, other top-level edits, missing/non-boolean flags and the absence of the explicit policy without modifying fixture files. The observed baseline manifest lacks an explicit maintenance flag; normalizing it to `false` before such a transition is a **separate unqualified managed change**, not an assumption that current beta already matches the fixture. This limited policy does not authorize a release, overlay or issuer switch. The modified inventory source requires a new reviewed launcher bundle and pin.

`tests/opfs-real-controller-test.py` uses pinned byte-checked copies of `webctl_live.py`, `common.py`, its helper modules, `scaffold_live.py`, and `sites_live.toml`, plus the actual revised `RenderInventory`, `ManagedWebctlAdapter` and version-2 gate Transaction. It redirects the copied controller's paths, users, systemctl and Caddy process calls to a disposable directory and local Caddy. The generator's full raw production output outside the beta block is byte-identical before/after; a deterministic test-only transformation relocates ports, log paths, proxy endpoints and Caddy administration to loopback. The fixture starts a real HTTP main-service stub, fsyncs a disposable protected backup, validates and reloads both actual generated prepare/production Caddy outputs through copied `webctl.caddy_apply`, and checks all 14 auxiliary render targets. A forked process dies after the gate reload; injected unknown manifest drift is rejected while the journal is retained, then gate-only recovery succeeds, beta returns maintenance, and main `/healthz` still reaches the stub. One existing host flock covers the nested Transaction.

This is a concrete local controller integration, not an installed protected launcher. It uses a fake timer, stubbed services and test-only output/path transformations. It does not establish actual systemd restart behavior, real issuer switching, actual deployed account/key custody, live HTTPS/main response preservation, actual protected release installation, uncooperative writers, power-loss guarantees, or production capacity. The Caddy fixture's backend thread and fork produce a Python multithreaded-fork warning; the bounded test completed, but this is not evidence that such a pattern is suitable for production. The generic old-journal bypass and other controller entrypoints still require floor enforcement.

## Pre-floor absent-to-false normalization

`RenderInventory(normalize_maintenance=True)` is a separate, narrow opt-in policy: beta must already use the identical configured release, the old maintenance key must be absent, the new key must be the boolean `false`, and all other manifest data and site entries must match. Both complete manifests are validated by their pinned generators. Every generated prepare/production Caddy output and every generated site-unit output must be byte-identical; otherwise construction fails before writing. All earlier default and maintenance-toggle policy behavior remains unchanged. Negative controls cover release, site and unrelated-field drift, missing/wrong/non-boolean flags, default policy refusal, and altered Caddy or unit output, with no writes.

The copied-controller local fixture now starts from the exact pinned manifest **without** the flag. It forks and interrupts the ordinary version-1 normalization after the manifest write; the actual managed transaction restores the original absent-key manifest, leaves the v2 floor absent, and preserves all auxiliary outputs and the main stub response. A failed readiness preflight likewise changes nothing and leaves the floor absent. A successful ordinary normalization then produces the explicit `false` manifest, leaves the floor absent, and verifies the byte-identical inventory before the separate gate-only recovery scenario. The test driver explicitly refuses normalization if a floor exists; production launcher enforcement, exact host pins, real timer/systemd, crash-restart orchestration and actual install remain unqualified. The fixture remains isolated, with paths/processes redirected and a real local Caddy process.
