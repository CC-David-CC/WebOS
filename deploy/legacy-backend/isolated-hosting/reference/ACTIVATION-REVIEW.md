# Beta hosting activation review — not an executable rollout

There is **no reviewed command that safely activates this candidate yet**. The current controller has no beta-desktop profile; `webctl.py up beta.ksu.codes` is not applicable, because beta is not a `[[sites]]` entry, and a newly disabled production hostname is deliberately refused. The old `activate-simplified-hosting.py` targets `ksu.codes`, not beta, and relies on the user-replaceable hosting lock. Do not run it or hand-edit `/etc/caddy/Caddyfile`. This document identifies the exact managed operations a future reviewed beta controller must perform, rather than supplying a misleading command.

## Required work before a controlled rollout

1. Independently review exact `ops/common.py` changes against freshly read live generator and manifest. Confirm source checkpoint, complete static release integrity, and full main-site rendered Caddy output is unchanged except the beta virtual host. Beta services must already exist as separately configured, protected processes using beta-bound origin/keys/policies, independent cookie secret, SQLite databases, user homes and service credentials. Confirm their precise process IDs, socket ownership, units, no drop-ins, config/manifest pins, loopback listeners and health under a temporary local test. Confirm public beta is not already claimed by an unrelated virtual host or certificate route.
2. Enforce `--no-guest-network` on the beta guest service and verify its config omits `guestNetwork` and its own endpoint denies it. Candidate Caddy independently returns 503 for `/guest-network`. The phase-aware worker currently lacks chunk/delta sync; do not describe it as implemented. Beta rate limiting and optional services such as speech and external app sandboxes need explicit configuration or honest unavailability.
3. Resolve the hosting controller-lock custody issue or establish another reviewed coordination protocol used by all concurrent hosting operations; an unrelated root-only lock is not sufficient. Define lock order with the native/file/storage managed operators, avoid acquiring their non-reentrant locks twice, and do not run a Caddy reload or leave partially written config if a prerequisite changes.
4. Build a Git-first reviewed activation controller under an immutable trusted path. With fresh exact generator/manifest/Caddy and service pins held under the reviewed locks, it must snapshot current `common.py` and `sites.toml` via the existing `webctl.snapshot`, import and validate the reviewed candidate generator, apply the single top-level `codi_beta_simplified` setting, and render full prepare/production configs. Validate the actual candidate Caddy configuration with the real protected imports as the `caddy` user using the controller's `webctl.caddy_validate` semantics. DNS/cert/route/health gates must pass; no separate webapp account/service should be invented merely for this top-level profile.
5. The existing controller's managed apply operation is `webctl.caddy_apply(data, 'production')`: it renders, writes managed Caddy candidates, validates as `caddy`, atomically selects the configured generated file and reloads Caddy with rollback of the prior Caddyfile on reload failure. A reviewed wrapper must also preserve and restore the generator and manifest snapshots if any later step fails. Calling `caddy_apply` alone is insufficient because it does not transactionally restore those sources. Record backup paths, hashes, receipt and current journal status before and after; preserve all main and beta data. A Caddy reload may close in-flight connections.
6. Verify real publicly trusted HTTPS and hostname, beta account registration/sign-in, beta cookies, signed file create/edit/CAS/reload, main↔beta token rejection and file/account isolation, and the guest-network block from a separate network where available. Check root-scope Service-Worker-Allowed header, browser storage, terminal and app CSP on desktop/phone. Recheck every pre-existing site's expected status, active PIDs/configs and `/desktop` bytes. No user account or data should be wiped to perform these checks; delete only confirmed disposable test fixtures.

## Rollback and limitations

Rollback needs a reviewed controller that takes the same safe coordination locks, checks fresh pins, restores the exact **activation-created** generator and manifest backups, regenerates/validates through `webctl.caddy_apply` and verifies all sites and certificates. `webctl.py caddy-rollback` alone only restores Caddy configuration and can leave generator and manifest inconsistent. Never roll back or erase beta/main account stores, keys, permissions, databases or files as a route rollback.

The available tests validate generated configuration, a beta-only disposable TLS endpoint and signed browser flows against separately assembled test services. They do not exercise production ACME, router WAN, actual root/systemd custody, the complete desktop application graph, real phone input, concurrent hosting mutations, or controller crash recovery. The generated profile and backend services have not been installed or activated.

## Bounded maintenance-window option — review only

At one read-only inspection, no running process matched `webctl.py`, hosting activation, `webhost-sites/ops`, Caddy reload or Caddy adaptation; the `dflanag3` crontab was absent, and inspected system crontab/cron directories contained no matching Codi/hosting entries. These snapshots do not establish that no other privileged or unrecognized writer exists or will start. The scheduled `codi-ksu-live-root-renew.timer` was **enabled, active, waiting**, with next run 16:00 EST; its oneshot service was **failed, MainPID 0**, and its command uses the existing hosting controller lock. These values will become stale and its prior failure needs separate investigation; do not reset its failure state as a side effect.

If a separately reviewed and explicitly authorized maintenance window is chosen, record the exact timer ActiveState, SubState, UnitFileState, loaded unit definition and hash, next-elapse observation, and current oneshot state before touching anything. Temporarily stop the **timer**, without disabling it: `sudo -n systemctl stop codi-ksu-live-root-renew.timer`. Verify it is inactive, then verify the corresponding service is not running; allow an already-running renewal to finish or abort the window rather than kill it mid-update. Check all other known scheduled/manual writers and enforce a supervisor/operator freeze for the full window. Acquire the existing hosting lock only after timer quiescence, verify the locked descriptor and pathname still match, and check source/config/generated Caddy pins and all relevant journals at every write boundary. Refuse unexpected drift and retain the review/recovery evidence rather than restoring over a third-party change.

In every success/failure/recovery exit path, restore the timer's prior **active versus inactive and enabled versus disabled** state exactly: if and only if it was active before the window, `sudo -n systemctl start codi-ksu-live-root-renew.timer`; do not enable, disable, mask, unmask, reset-failed or start the oneshot unless that was separately authorized. Verify post-state and unit definition match the recorded prior state. A timer's next scheduled timestamp may naturally change when restarted; matching active/enabled state does not restore an elapsed schedule or erase a missed event. If the process crashes before restoring it, a durable root-owned recovery record and independently verified operator recovery procedure are required. These commands are procedure inputs only and have **not** been run.

Even with process inspection, quiescence and before/after inode/hash checks, the current user-writable hosting-lock ancestry permits a non-cooperating local writer to swap a path between a check and rename. File check plus rename is not an atomic compare-and-swap; therefore this bounded approach cannot prove that it will never overwrite concurrent uncooperative edits. A genuine no-overwrite guarantee needs protected shared lock custody used by every writer, or an independently enforced quiescence boundary. No beta activation controller or durable timer-restoration journal has yet been qualified against the real host.

`tests/fixtures/maintenance_transaction.py` and `tests/maintenance-transaction-test.py` are an executable **disposable model**, not a host controller. Five isolated tests exercise coherent success, preservation on observed drift, detection of replaced lock, process death before/after a modeled commit, and restoration of modeled timer state. One intentionally passing negative control demonstrates that a non-cooperating writer between the check and replace can be overwritten. The model omits actual systemd, Caddy validation/reload, route and issuer preflight, root custody, unit/service readiness, real timer behavior, health checks and the managed webctl adapter. It is not safe to invoke on host configuration or evidence of a deployable controller.

`ops/beta_transaction.py` now contains an executable transaction core and a `ManagedWebctlAdapter` that dispatches generated configuration through `webctl.caddy_apply` rather than editing Caddy directly, plus a systemd timer adapter. The core journals old/new bytes and timer state before stopping the timer, refuses observed drift and unavailable beta preflight, preserves the journal on interruption, and distinguishes prepared recovery from committed recovery. `tests/beta-transaction-test.py` passes six disposable fake-adapter checks; the earlier separate six maintenance-model tests include an explicit non-cooperating-writer race negative control. The adapter requires trusted, pinned generator/webctl modules, an independently reviewed lock context, beta readiness and full site-health functions, and a root-protected journal parent supplied by a **separate protected launcher**. No such launcher or actual beta backend provisioning/health adapter has been implemented or reviewed yet; the Python classes must not be used on the host. Fake webctl/systemd tests do not establish real unit behavior, recovery, source custody, root privileges or crash durability.

Independent review identified additional core gaps; the current candidate requires a main-site health check before commit and after recovery, refuses Caddy start/enable/unmask/restart through `webctl.run`, and requires launcher-provided Caddy active-state and **complete auxiliary render-target inventory/hash checks** before calling the real `webctl.caddy_apply`. Recovery journals whether Caddy apply started and re-renders derived outputs when needed. The inventory checker, protected launcher and actual backend health checks remain unimplemented; requiring a callback does not establish that it is correct. Timer stop and a quiescence snapshot also cannot exclude a manual service start without the maintenance freeze. No source here is approved for host execution.
