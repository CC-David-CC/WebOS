# File ingress production-candidate design — research only

This is a proposal, not a release or authorization to change the live host. The `tests/layered-file-gate-*` module is an experiment and must not be installed as an ingress. See `evidence/light-file-100-session-20261102.md` for measurements, failures and caveats.

## Existing path and measured problem

Read-only inspection on 2026-11-02 found Caddy 2.11.4 routing `/gateway/*` to `127.0.0.1:8140` with a 192 MiB request-body cap and no explicit route-level reverse-proxy transport override. That socket is managed by systemd: `Backlog=16` and `systemd-socket-proxyd --connections-max=16`, forwarding in the private gateway network namespace. It uses an unprivileged dynamic user and existing systemd filesystem, capability, address-family, task and memory restrictions. The active gateway launcher defaults to 2,048 shared POSTs per fixed minute. Gateway operation admission is four active slots, 128 waiters, five-second wait; signed proofs, current authorization and quotas remain mandatory. Browser mirror retry and locally retained pending state already exist. The fixed socket proxy and the managed hosting/controller framework are available; Caddy's installed modules do not include a rate-limit handler. Source and installed versions must be re-pinned immediately before any implementation.

In isolated tests, four held signed uploads occupied all four gateway slots; 100 synchronized light checks failed (87 gateway-path 502, 13 gateway 429). Sixteen incomplete unauthenticated challenge bodies also saturated the shared proxy/operation path. A test-only streaming gate showed light-work progress in those controlled cases, but it is not production-ready. Important fixture correction: its locally created socket used `listen(128)`, whereas the inspected live systemd socket specifies **Backlog=16**. Its 16 active proxy connection cap matched; its connection backlog did not. Reproduce with the actual backlog and configured runtime before attributing exact failure counts to production.

## Candidate architecture for review

1. **Use existing managed ingress, not a public new listener.** Preserve Caddy's domain/root and `/desktop/` boundaries and protected generator/manifest workflow. Keep the existing loopback ingress, namespace isolation and trusted-origin enforcement. First assess whether separate managed systemd socket-proxy instances and Caddy path handlers can provide lane isolation without weakening current Caddy or private-network boundaries. If existing Caddy/systemd facilities cannot bound pre-handler connections and queues or safely authenticate claims, a small independently reviewed admission service may be necessary; do not install the test gate. Any new loopback sockets/units are internal operational changes requiring pinned, reversible managed configuration, not external router ports. Measure their combined resource use and ensure these routes cannot reach private user data except through the existing gateway.
2. **Bound ingress before expensive work.** Set reviewed limits on accepted connections, request-header size and time, concurrent body readers, total bounded queue, queue time, and per-route body size/read progress at the actual first handler. Do not assume Caddy's default transport or a local TCP proxy provides a bounded authenticated queue. Keep an overall request/rate ceiling and explicit cgroup/file-descriptor/task/memory limits. Return a controlled overload response, with an unambiguous pre-dispatch indication only when it is true. A slow sender must not reserve the whole upstream pool. Challenge bodies are small and can be read to a bounded buffer; set their deadline from measured mobile/network conditions rather than adopting the prototype's arbitrary two seconds. Require unambiguous methods, paths, content lengths, Host/Origin and unique security headers; reject transfer-encoding ambiguity and oversized bodies before forwarding.
3. **Reserve capacity in both proxy and gateway.** Evaluate separately bounded challenge, short metadata/use and transfer lanes, with a fixed aggregate ceiling and at least one independently protected short-operation lane. If the 16-connection proxy remains shared ahead of those lanes, slow requests can exhaust it before gateway reservations help; either place bounded classification ahead of that boundary or use separate managed proxy sockets with explicitly bounded combined capacity. Validate that gateway's own four-operation admission cannot allow transfers and small-body stalls together to consume every short-operation slot. Small `/gateway/use` requests still need authentication before their trust can be assessed; even reserved lanes can be attacked. Large legacy encoded `/use` bodies and streamed `/upload` must use transfer budgets without reducing the 128 MiB file limit. Do not buffer full uploads at ingress; stream in bounded chunks, retain inactivity/deadline/pacer limits and allow genuine slow mobile transfers where measured safe.
4. **Keep authorization and state authoritative.** Do not classify a user by an unsigned key, username, browser-supplied forwarding header or shared-NAT IP. Preserve the current signed one-use challenge/grant/proof, subject/session/key and policy-generation checks, filesystem permissions, size/quota checks, hash verification and expected-version/CAS behavior. Never consume a one-use proof while waiting for admission. A capacity rejection before any dispatch may be explicitly marked as such; once dispatch or commit is possible, report an uncertain outcome and reconcile before retrying a mutation. On cancellation, disconnect, timeout or crash, close both stream ends, remove only temporary data, release every lane and ensure no partial file becomes visible. Keep user data and account state untouched during config rollout.
5. **Consider account fairness only with a verified identity.** The existing `docs/GATEWAY_FAIR_ADMISSION_DESIGN.md` and source-only `experimental_admission.py` explore issuer-signed short-lived tickets and verified/legacy/unverified shares. Review and test that design before using it: bounded table/verification work, trusted audience/key and exact request binding, replay and expiry, revocation window, key rotation, account budgets across workers/restarts, downgrade-safe capability negotiation, and protection against a single account, many accounts, forged proofs and shared NAT. A ticket is admission evidence, not a file permission. Maintain a global hard ceiling. No scheme can classify an unauthenticated connection for free, and no guarantee of availability under arbitrary floods is implied.

## Required test gates

All initial runs use isolated accounts, disposable state, loopback/private test routes, fixed duration, request ceilings, CPU/RSS/disk/file-descriptor/connection monitoring and external stop guards. Record raw failures as well as retry outcomes, phase timings, observed concurrency/queue depth, HTTP status and transport errors, p50/p95/p99/max, actual synchronized versus idle distribution, gate/gateway/Caddy/proxy resource peaks and cleanup receipts. Use exact pinned binaries, generated config, proxy `Backlog=16`, live-equivalent caps and explicitly identify any deviations.

- **Correctness and compatibility:** actual browser capabilities/GETs, login and file operations; old/new client negotiation; ordinary JSON and streamed binary paths; exact 128 MiB and oversize rejection; content hashes, conflicts and independent account isolation. Verify missing/duplicate headers, malformed/partial JSON, invalid lengths, protocol smuggling, extra/forged forwarding headers and path normalization do not bypass limits or consume an unrelated proof.
- **Slow legitimate clients:** physical phones and emulated mobile networks, including high latency, variable bandwidth, pauses and reconnects; simultaneous small work plus several independent uploads and downloads, including exact 128 MiB. Record transfer progress, success, backpressure, file/hash integrity and user-visible pending state. A provisional body timeout is unacceptable until legitimate slow-client results support it. Do not confuse a slower successful transfer with a hang.
- **Stall and saturation controls:** repeat the four held uploads and 16 incomplete unsigned challenges through actual Caddy, managed-equivalent proxy sockets and candidate lanes, then try slow headers, valid/invalid short `/use` bodies, stalled long bodies, a saturated verification lane, authenticated abuse and 100 unrelated sessions sharing NAT. Show how many light operations complete or fail and their p99 while transfers remain active; test simultaneous legitimate transfers remain bounded. Re-run against unchanged baseline and retain failures and 502/429/reset counts.
- **Cancellation, crash and proof safety:** disconnect at each admission/read/write/commit phase, race repeated cancellation and shutdown, kill/restart services with queued and in-flight work, rotate keys and revoke/disable sessions; verify bounded cleanup, no stale permits, no partial publication, no proof misuse, and correct fresh-proof behavior. Test full disk, quota exhaustion and timeouts; never retry ambiguous writes without reconciliation and CAS.
- **Capacity and fairness:** after isolated setup, maintain approximately 100 independently authenticated sessions with realistic idle jitter, a small active subset, repeated signed file checks and occasional small edits over multiple rate windows. Add bounded reconnect/login bursts and a few slow/large transfers. Run malicious load separately and verify a single account cannot consume another's reserved budget while global limits still hold. Measure CPU, memory and connection headroom on target hardware; avoid claiming a 100-user capacity from one browser or one short burst. Agree on numeric latency, error and resource thresholds with observed baselines before declaring the gate passed.
- **User experience:** verify My files preserves local drafts and communicates pending/error/conflict truthfully; failure of ingress, Caddy, socket proxy, issuer or gateway must not claim a server save. Exercise browser retries and a real TCP reset, not only an injected JavaScript exception. Include 30 simultaneous classroom logins separately; file and identity paths compete for host resources.

## Rollout prerequisites

Independent security and operations review must cover the complete path, same-NAT and adversarial threat model, actual account isolation and proof/ambiguous-write semantics. Prove deterministic configuration generation, exact input/binary hashes, no secret or account-state copies, forward/rollback and crash recovery under the hosting controller lock. Stage an isolated candidate, perform the test gates and compare all site health plus running service identity before any activation. Prepare a scoped rollback that preserves account files and states; Caddy/proxy restart may interrupt in-flight streams and must be planned and verified. Do not claim live readiness, enable a route or expand publicly until the candidate is independently approved and the user-authorized rollout is ready.
