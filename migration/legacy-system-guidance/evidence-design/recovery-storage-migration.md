# Recovery storage migration: implementation constraints

Status: design for an experimental change, not implemented or deployed. The current recovery voter cannot safely rely on a separate checkpoint journal to prove that a device's normal archive has not advanced.

## Existing boundaries

`DeviceChannelArchive` uses database `codi-device-channel-archive-v1` version 1, with `nodes`, `heads`, `pending`, and `accounting` stores. Its authenticated current state is reconstructed from a verified checkpoint, operation index, and history node. Accepted head changes occur in the read-write transactions for block acceptance and checkpoint installation; filling a historical gap also rewrites a head row. All use a compare-and-swap against the previously read head hash. `OfficialRecoveryNewVoter` writes its anchor to a different database, while `OfficialRecoveryVoteJournal` writes its vote to the replica-key database. IndexedDB transactions cannot span these databases.

## Proposed coordinated archive version

1. Add a version-2 archive store with one fence per account scope and channel, alongside the existing stores. Migrate version 1 in the version-change transaction without deleting or rewriting prior records; validate schema and accounting before use. Existing version-1 connections must close on `versionchange`; software that explicitly opens version 1 after migration must fail rather than silently ignore the fence. Test blocked upgrades and interrupted upgrades with preserved data.
2. Verify the channel checkpoint, membership and signed recovery proposal outside the write transaction. In one strict read-write archive transaction, compare the exact authenticated local head row hash and install the proposal's recovery fence only if the local head matches. A missing normal archive or genesis-only local history must not be silently treated as proof of the proposed checkpoint; synchronize and verify it first. A conflicting existing fence fails closed, while an exact retry is idempotent.
3. Every operation that changes the accepted head must read that same fence inside its existing read-write transaction and refuse changes while fenced. This includes ordinary block acceptance and checkpoint installation; gap repair must be explicitly classified because it can rewrite the stored head without advancing the accepted position. Enqueueing pending originals and read-only access should remain available where safe. Test every head-write path, concurrent races in both orders, exact retry and rollback on transaction failure.
4. Only after the archive fence commits may a validator sign and durably journal a recovery vote. A crash between fence and vote leaves a safely paused channel; exact proposal retry may finish the vote. A signed vote must never be returned before its own strict commit. This ordering is not a cross-database atomic transaction: old code, account storage deletion, full-profile rollback and manually released or inconsistent fences need explicit policy. Do not clear a fence automatically just because the voter did not finish.
5. Provide an explicit, authorized recovery transition and retirement protocol before resuming normal writes under a new committee. Do not treat a stored certificate or a local fence as a completed channel transition. Old and new versions, disjoint/overlapping validator groups, loss of keys and offline peers require their own safety and liveness tests.

## Required tests before integration

Use real browser IndexedDB and distinct profiles: preserve an existing version-1 archive and accepted messages across upgrade; old and new tabs during `versionchange`; interruption before and after commit; ordinary acceptance racing fence installation; checkpoint installation racing it; stale checkpoint refusal; same-head idempotent retry; later-head and competing proposal refusal; crash before vote, after vote, and browser restart; all affected writes reject while fenced; other channels and pending inputs remain usable. Verify that quota and deletion/accounting remain correct and that abandoned fences have an explicit operator recovery path. Finally exercise the actual member RPC and normal session wiring, multiple validators, and independent networks. None of these tests is represented as already passing by the earlier fixture-only recovery tests.

Initial source-only helper `assets/desktop/experimental-recovery-archive-schema.mjs` and `.build/checks/recovery-archive-schema-r2.json` exercise a v1→v2 IndexedDB upgrade against representative fixture rows, connection versionchange, old-version refusal and malformed-schema abort. The real archive still opens v1, so running the helper on actual data would make the current app unable to open it. No fence or actual signed-archive migration is yet implemented; do not deploy this helper by itself.

`.build/checks/recovery-real-archive-migration-r2.json` PASS local actual signed chat block in a v1 archive, schema upgrade, and re-verification of preserved checkpoint, index and history by a fixture-adapted v2 reader. This is not yet a migration of the normal archive implementation or enforcement of recovery fences, nor a crash or retention test.

`.build/checks/recovery-archive-fence-r1.json` exercises an experimental strict transaction that compares the saved archive head hash and stores an idempotent fence in the same v2 database. A fixture-adapted archive blocks a real valid signed append after insertion. The fixture blocks all writes, and the primitive trusts its caller's hashes; concurrent racing, correct per-write behavior, authority validation, vote coordination and production migration remain outstanding.

Fence checks were injected into all three head-write methods but only append was exercised; primitive remains unauthenticated and unintegrated. No production migration or WAN test.

The wrapper depends on caller-provided archive/scope/database, only supports generation zero, and the raw unauthenticated helper remains available. Fixture-only v2 code; no normal app or voter integration, service authorization or deployment.
