# Official-channel controller recovery: design constraints

Status: design work, not implemented or deployed. Official channel history can be stored by the server, but the current controller and validator identities are fixed in the signed genesis policy. A browser's controller key is nonextractable, and clearing its site data destroys it. The live official directory has no enrolled channels.

The controller key authorizes moderation, permissions and account-control proposals. The validator keys separately authorize accepted blocks; a copied validator key without its latest durable voting state could sign conflicting votes. A controller backup alone cannot repair a lost sole-validator channel. Account-device enrollment grants member permissions but does not transfer either authority.

A durable solution must define a new signed policy/version with an explicit, limited recovery authority, and browser and official-server verifiers must implement the same rules before the server accepts it. Recovery must bind the channel and genesis, the last accepted head, the old and replacement authority, and a monotonic generation; it must reject replay, stale heads, unauthorized signers and conflicting replacements. Validator changes require a joint transition accepted by both old and new committees, or a separately specified disaster-recovery authority with explicit conflict rules. No ordinary account login or server directory entry should silently grant channel authority.

Recovery material must be protected independently from browser storage, have an explicit operator-controlled backup and restore path, and avoid cloning live validator keys or discarding their durable vote fences. Existing nonextractable channel keys remain unchanged. A first implementation should use separate recovery keys and rotate to fresh validator keys, with explicit failure when an authorized recovery cannot safely establish the last accepted state. Device-owned user channels should not silently gain a server recovery authority.

Required proofs before activation: deterministic JS/server replay parity; invalid signature, wrong channel/genesis, rollback, duplicate and stale recovery rejection; two competing recovery attempts; interrupted and retried durable commit; fresh device restore with prior browser unavailable; old validator unable to create an accepted competing continuation; service restart and peer convergence; full chat and moderation after recovery; private key and voting-state custody; version negotiation; cleanup; and test of an actual managed official channel. A single-provider outage or an inaccessible quorum must be reported as pending, not as evidence authorizing takeover. All of these remain open.

A local experimental proposal codec now exists in `network/official-controller-recovery-proposal.mjs`. It verifies the pinned recovery-key signature, replacement-key possession and exact trusted channel/genesis/head/controller/generation binding. `scripts/official-controller-recovery-proposal-check.mjs` passes positive and negative Web Crypto checks. This is not a policy, a durable transaction, validator rotation, or authority to modify existing channels. Two separately valid proposals against the same trusted state both verify until an atomic authority chooses and commits one; the test explicitly checks this. An attacker-supplied context is not trusted merely because this function accepts it. The proposal's replacement is a controller identity only: it does not authorize copying or reusing a validator's key or voting state. Server-side parity and actual consensus transition remain unimplemented.

`steward/official_controller_recovery_proposal.py` now independently verifies the experimental proposal profile with Python's cryptography implementation. `scripts/official-controller-recovery-parity-check.py` generates 17 Web Crypto signed cases and compares both implementations, including valid and competing-valid proposals and invalid scope, generation, signer, possession and malformed fields; both accept two and reject the rest. This is one-directional generated test coverage, not comprehensive adversarial parity, trusted policy provenance, transaction serialization or integration into official history replay. No verifier in the live official service uses this module.

`steward/official_controller_recovery_journal.py` adds an isolated experimental SQLite selection journal. `scripts/official-controller-recovery-journal-check.py` PASS locally checks a thrown precommit interruption, process death before commit, two competing signed proposals submitted concurrently to one database, exact retry, stale competing proposal, and reopening the selected state. Its initialization trusts a caller-supplied context and it neither tracks live history heads nor coordinates other servers or validators. It does not establish channel authority, prevent a competing network branch, fence old validators, prove power-loss durability, or integrate with production. Never use this local selection as a substitute for a verified consensus transition.

`network/official-controller-recovery-certificate.mjs` is an isolated experimental joint-committee certificate checker: it verifies both signed proposals/possession and distinct pinned old/new committee signatures, each with n−floor((n−1)/3) votes. `scripts/official-controller-recovery-certificate-check.mjs` PASS covers quorum, duplicate voters, signature, sorted identity and proposal binding. The test also deliberately has the same signers sign two different proposals and confirms that both certificates verify: signature verification alone cannot prevent equivocation. The provided vote-signing helper is test-only and must not be used as a production voting API. Durable per-validator vote fencing, trusted policy membership, candidate committee authorization, old/new transitions, independent peer verification and server parity are not implemented; the module is not imported by live code.

`assets/desktop/official-recovery-vote-journal.mjs` is an isolated prototype using the existing strict IndexedDB replica journal and key fence. It saves a channel-key-signed vote before returning it, uses a single fence for both committee roles per channel/genesis/generation, retains exact votes on retry, and rejects a different proposal. `scripts/official-recovery-vote-browser-check.py` PASS using real Chrome, persistent storage and SIGKILL/reopen: same vote survives, conflicting other-role vote is refused, same proposal can receive the other role, and both fenced votes form a single-member joint certificate. The checker rejects raw unfenced test votes unless explicitly enabled for its fixture. This assumes the caller already authenticated recovery policy and committee membership; restoring an old entire browser profile or same-origin malicious code can bypass local fences. It does not fence ordinary channel voting, prove quorum safety during view changes, install new membership, or activate a network transition. No live code imports it. Initial browser test timed out due to a synthetic click failing the native persistence gesture; corrected to use WebDriver click and subsequent runs passed.

The local Chrome fence test now also starts two independent journal instances on the same signing identity and races different recovery proposals: exactly one returns a vote and the competing proposal is subsequently refused. The existing IndexedDB compare-and-swap transaction provides that exclusion within the same browser storage domain. It does not coordinate the separate normal channel-voting journal: an old validator could still produce ordinary channel votes after this recovery vote. Recovery finality therefore remains unsafe until normal voting and recovery retirement share a verified atomic fence and a jointly accepted history transition. No runtime integration.

The shared replica journal now has an optional bounded transaction guard: a write can require another journal record for the same actor/scope to have a specified hash (or be absent), checked inside the same IndexedDB transaction as its own write. Guard checks refuse missing/mismatched key fences. An actual Chrome fixture races two synthetic guarded records in opposite domains: exactly one commits; deletion of the winner's row while its key marker remains makes the other fail closed; then the fixture restores its intentionally damaged row. Existing actual-browser replica regression `.build/checks/replica-guard-regression-r2.json` PASS39, including SIGKILL recovery and competing normal prepares. The recovery and normal protocols do not yet pass these guards, and the test uses synthetic state rather than actual normal prepare versus actual recovery. This primitive alone does not prove safe retirement or transition. No deployment.

Experimental opt-in wiring now connects the guard to the real `DeviceReplica` and recovery vote methods. A validator started with `experimentalRecoveryGeneration` guards every journal mutation against the corresponding recovery vote record. `experimentalRecoveryFence()` supplies its exact journal hash and accepted head only when there are no outstanding prepared values, votes, or view promises; a recovery vote can include that fence and atomically guards against a changed normal record, while checking the saved head matches its proposal. `scripts/official-recovery-vote-browser-check.py` PASS on actual local Chrome for a normal prepare first, recovery vote first, and both racing: exactly one returns, and the other cannot proceed. Also covers recovery vote restart and cross-role conflict. Ordinary production validators do not opt in, recovery's guard remains optional in the experimental class, a caller can supply unauthenticated context/fences, and this does not establish committee membership, cross-device exclusion, quorum intersection, a committed membership transition or retirement against old clients. Do not deploy this wiring as recovery. `.build/checks/replica-recovery-optin-regression-r2.json` PASS39 with opt-in disabled; r1 fixture missed a new import and timed out, corrected by deriving the shared domain without adding a fixture dependency.

Six local Chrome profiles with separate keys now pass an overlapping old/new committee quorum check (`scripts/official-recovery-quorum-browser-check.py`); fixture automation carries the votes, not RTC. Each group of four requires three, and a restarted voter retains exact signatures. The current signed proposal does **not** commit to either committee list; both lists are caller-supplied to the verifier. Binding the authorized current committee and exact replacement committee into the recovery authority proof is required before this can authorize a real membership change. Normal-vote fencing was not exercised in this six-profile test.

The experimental proposal now commits to SHA-256 identifiers for the exact sorted old and new committee actor lists, and the certificate verifier independently derives those identifiers from its supplied keys and refuses mismatched lists. A six-profile browser quorum test passes with different overlapping four-member committees, both insufficient quorums refused, an attempted replacement list substitution refused, and one voter crash/restart. Proposal JS/Python parity passes 19 cases including changed old/new committee commitments; local selection journal and one-browser normal/recovery race tests pass. These commitments rely on a caller-authenticated trusted context; no existing genesis policy supplies one. The experimental local selection journal does not yet derive the next generation's authorized committee after a selection. No actual membership transition, P2P transport, server replay integration or deployment.

Experimental `network/official-controller-recovery-policy.mjs` defines a signed recovery-policy attachment bound to the original channel/genesis and a recovery public key. Given an independently authenticated attachment hash and an actual `deviceChannelPolicy`-verified position, it checks the owner signature and derives the original committee from the signed genesis policy, verifies the supplied keys match its actors, and commits a proposed new committee into the recovery context. `scripts/official-controller-recovery-policy-check.mjs` PASS local Web Crypto: correct owner/pin/position and original group, wrong pin/owner/old group and forged position rejection, and integration with proposal plus a deliberately unfenced test-only joint certificate. This does not authenticate where the attachment pin comes from: existing channel genesis/listing does not contain it. Competing owner-signed attachments, real fenced committee votes, checkpoint provenance across history, later generations, Python parity, transition/finality and deployment remain open. Initial test failed at JS parse before effects and was corrected.

The six-profile `scripts/official-recovery-quorum-browser-check.py` now composes a real browser-held owner key, signed channel policy and signed recovery attachment; each independent browser verifies the channel/genesis and attachment, derives the old committee and proposed new commitment, then persists real fenced key proofs. PASS includes wrong attachment pin, either insufficient quorum, altered membership, joint quorum and one browser SIGKILL/reopen. The fixture provides the attachment hash and carries wires between profiles; the old group does not vote on an existing live channel and the test does not authenticate pin distribution, exercise RTC, guard actual ordinary votes for this multi-profile case, or commit a transition. No deployment.

To avoid circularly hashing an attachment that itself includes the genesis hash, the local source now supports an explicit `recovery` public key inside an opt-in signed public-chat genesis. `genesisOfficialRecoveryContext` derives the owner and recovery key from a verified position, the original committee from that signed policy, and the proposed new committee hash from provided public keys. Real Web Crypto validates the recovery key lies on P-256 both when creating and reading the policy. `scripts/official-recovery-genesis-check.mjs` PASS checks opt-in policy, invalid curve and forged position refusal, legacy policy acceptance and an older compiled reader refusing the new field; `scripts/official-recovery-quorum-browser-check.py` PASS six local profiles independently reading signed opt-in genesis and assembling fenced quorum; `.build/checks/genesis-recovery-legacy-replica-r1.json` PASS39 legacy replica regression before the additional key-curve validation (which affects opt-in only). Existing official server/listing verifiers reject the new policy and no capability negotiation or generation transition exists. Existing live channels are not upgraded, and no changes are deployed.

`steward/official_recovery_genesis.py` now independently verifies the experimental public-chat recovery genesis, its owner signature, pinned genesis hash, sorted validators and valid P-256 recovery key. `official-recovery-genesis-parity-check.py` PASS10 compares Python and Web Crypto for one valid and nine invalid browser-signed cases, and `official-recovery-genesis-python-parity-check.py` PASS verifies a Python-signed genesis in both implementations with identical initial head and policy fields. `network/official-controller-recovery-authority.mjs` prototypes an in-memory, branded recovery-authority chain. The initial state derives from a verified recovery-enabled channel position and signed genesis committee; advancing verifies the exact proposal, possession and both fenced quorums, then derives the next generation/controller/committee and a transition hash independent of vote ordering. The six-profile browser fixture passes with two distinct profiles deriving the same transition, replay and fabricated authority object rejected. Fixture supplies wires and pinned genesis; this is not persisted, accepted by normal channel state, independently replayable after history changes, networked, server-verified, or proof that old validators are retired. Normal votes and recovery votes are not fenced together in this multi-validator test. No live integration or deployment.

`assets/desktop/official-recovery-archive.mjs` is a separate, experimental IndexedDB proof archive using the existing `DeviceChannelJournal`: it replays bounded recovery certificates from pinned signed genesis, enforces an exact prior proof prefix on updates, and re-verifies saved proof when loading. This archive has its own experimental scope; it is not the channel history, does not protect against whole-profile rollback, does not integrate later ordinary channel blocks or establish distributed finality, and is not deployed.

The experimental archive prefix check now compares each transition's signed proposal, possession proof and new committee rather than requiring identical ordering of its votes.
