## Actual first unsupported point

A generic selected-profile/holes/edge/Boolean part has no normal material-assignment entry point. Desktop `material-commands.mjs` registers only `inspect-enclosure-materials` / `assign-enclosure-materials`; Core `projectManagerBundle.ts:214` discovers only WORKER_ENCLOSURE_V1/V2. A generic part therefore yields no assignment candidate. `exportCore3mfResearch` at line462 first requires manufacturing metadata and otherwise refuses **Assign materials before exporting 3MF**.

Assigning generic metadata privately would not fix the workflow and is prohibited. After metadata resolution, the same function routes **any** Worker geometry to `workerEnclosure3mf`. That adapter admits only OCC enclosure binding types/roles and reconstructs the authored enclosure plan. It cannot manufacture generic MWorkerSolid bodies. The legacy route expects NATIVE_MESH_BOX or its specialized enclosure Boolean mesh; generic Worker box names/objects do not satisfy those adapters. Widening an allowlist or routing generic display triangles into this path would be false support.

## Existing mesh data is not manufacturing data

`MWorkerSolid` (`web/app/cad/model/mworkerSolid.ts:1`) describes ONE complete native result; it does not expose independent selectable solids/material regions. Its retained mesh is a private Float32 display projection and `ext.workerGeometry.quality` is **display-only**. It may be explicitly unavailable for Float32 collapse/overflow or unqualified SMLib material orientation. `solidLedger.mjs:136` reads `solid.mesh.read` for this purpose; controller descriptor at `worker-controller.mjs:56` expressly says qualification:unqualified/purpose:display-only. Even that operation's Float64 buffer is display-only, not a manufacturing-quality escape hatch.

The Native selected-owned reader `_ReadOwnedMeshV2` in `shape-io/selectedProfileV2.hpp:100` uses fixed `BRepMesh_IncrementalMesh(shape,0.05,false,0.4,false)` with1000face/100000triangle caps. It takes no requested manufacturing controls and meshes the queried shape's attached triangulations. Its measurements/topology do not establish an achieved surface-deviation bound. Old `main.cpp:289` UpdateTessellation accepts a raw native shape pointer; it is reference code, not an owned/candidate-authorized browser API. Neither is the proposed manufacturing seam.

## Proposed authored assignment contract

Reuse the existing optional native-envelope manufacturing record/version1 and manager-owned transaction, revision/hash Worker and Save/Open validation. Do not introduce a second model, geometry cache, provider, file format, mirrored material truth, physical-property engine or automatic material classifier.

1. Discovery returns an opaque document/material revision plus actual current bodyId, producer featureId, exact operation type, saved whole-part engineRevision, native result kind/count, placement and explicit support/reason. Resolve registry membership/current accepted model and producer history, not body ID grammar, array ordinal, face index or display mesh. Empty/unqualified/consumed outputs are not selectable. First generic slice: explicit OCC, current positive valid single-solid output, unplaced model; other engines/placements/multi-solid containers stay explicit unsupported until qualified.
2. The normal assignment operation accepts discovered identities, stable printable-part IDs/names, stable region IDs, existing authored binding alias, materialId/appearanceId and grouping. No geometry or mesh is supplied. App allocates new small alias/part/region IDs once; later assignments preserve them. Existing generic metadata binding shape `{id,featureId,operationType}` can represent a uniquely resolved complete output without a new schema. `region.bodyId` continues to reference that alias, not a raw kernel handle or new name grammar. Strengthen its resolution to actual MWorkerSolid/feature/registry/build/current-history custody; the current generic resolver's originatingOperation-only uniqueness is not sufficient authority for this new path.
3. A printable part is one eventual build item. A region is one explicitly selected homogeneous complete native output. Two unrelated outputs remain two separate printable parts/build items unless explicitly grouped. Several aligned regions in one part retain their shared source/model frame; no independent packing, centering, scaling, Boolean union or auto-order priority. No grouping a material subset of a generic multi-solid output by guessing native solid/face indices. No missing/duplicate region binding or exporting a consumed input.
4. Reuse materials `{id,name}` and appearances `{id,name,color}`; preserve caller-defined IDs, names, colors and pair associations exactly. They are labels/appearance, not density, safety or extrusion certificates. Null/unknown assignments may persist in the native project and remain visible; exporting an unresolved material/appearance refuses explicitly. Do not silently replace unknowns with PLA/PETG/white or infer substance from names. ID conflicts with different definitions refuse.
5. Assignment captures/detaches bounded own data before await, hashes captured authored project in the existing Worker, rechecks source/history/model/material/document/host custody, then publishes metadata once. It changes material/document dirty state, not authored geometry, source, feature counters, Native result/mesh or authored Undo history. Failure/cancellation leaves accepted metadata unchanged. Geometry changes invalidate assignment revision; proposal+explicit confirmation may preserve unique SAME producer bindings, but cannot silently bind a different child/body or repair ambiguity. Native Save/Open preserves exact IDs/unknowns and grouping through the existing envelope.
6. Initial cap:32 printable parts/32 total regions/128 exported material-appearance pairs, within existing writer limits and native preparation8MiB cap. Full native project admission is not narrowed by this export limit. Read-only discovery summaries remain≤64KiB; large geometry is binary/private, never a metadata JSON bypass. One region cannot be duplicated across two parts in the same export transaction.

Suggested normal APIs (names provisional until source ownership is approved): `inspectManufacturingParts`, `assignManufacturingParts` on the existing manager, with guarded public adapters; existing `inspect-manufacturing` and `export-core-3mf` remain normal shared routes. A human control must call the same assignment operation, not a provider/agent-only setter. Root owns host index/common integration; no such methods are implemented here.

### Aligned material regions need a real additional proof

Two regions in one printable part require no overlapping material interior and verified shared-interface/alignment in the same frame. AABB contact, equal transforms, zero reported common volume alone or a face-colored display are insufficient. Reuse the enclosure paired-contact discipline; add a narrow generic Native pair/interface verification over the TWO actual candidate-owned inputs. Common-with-history's lower-dimensional refusal must not be treated as empty/disjoint/contact evidence. Preserve both inputs; any Boolean/contact computation is ephemeral and never an authored cylinder/second model. For initial planar adjacent box regions, qualify real common interface area/orientation and mutually consistent interface tessellation; overlapping or unknown pair relations refuse. Separate printable parts must stay separate build items; grouping is never inferred from proximity or material name.

The existing writer's `validateShellNesting` admits overlapping shell bounds only for exact boxes. Curved nested cavities therefore remain explicitly unsupported until a verified native material-side/nesting proof can safely feed an appropriately guarded validator. Do not delete this refusal just because the BRep is valid or one solid. Likewise, generic curved multi-material interfaces remain unsupported until paired tessellation is qualified. These are unfinished acceptance domains, not passing rows.
